Say this first

The 2-minute pitch

Project 3 tried to animate a drawn character from a character sheet: cut it into body parts and move them with a motion library. The motion transferred to a new character with no new animation work, but the appearance broke: cutting a flat drawing into parts means guessing the areas hidden behind other parts, and those guesses showed as seams. Lesson: motion and appearance are separate problems.

Project 5 separates them. An AI agent directs animation inside Blender, real professional software, through 16 checked tools. Characters are stick figures, so only the motion matters. Every result is checked from Blender's own scene data, and a failing report goes back to the agent to fix.

Four directors, same tools, same 30 tasks: hand-written rules 30/30, qwen2.5 3b 3/30, qwen2.5 7b 8/30, Claude 30/30 (it fixed its own 3 first-try failures). Claude also directs multi-shot stories, e.g. a 54 s, 7-shot story in 44 tool calls with 0 errors, for about a cent per second of animation.

Concept

What is an agent? What makes this "agentic"?

A language model on its own only writes text. An agent is a language model placed in a loop where it can act on the world through tools, observe what happened, and decide the next step, until a goal is reached.

Part of an agentIn this project
GoalThe request, e.g. "a stick man walks to the table and waves"
Brain (policy)The language model: qwen2.5 3b / 7b, or Claude. (A0 is rules, not a model: the baseline.)
Actions (tools)16 functions such as add_asset, add_stick_figure, play_action, set_camera
EnvironmentA Blender scene, running headless
ObservationsEach tool's JSON result, scene_state, and error messages
Feedback / self-checkThe checker's report: which checks failed and why
StoppingThe model says it is done; the checker passes, or 3 fix rounds are used up

This pattern is ReAct (reason, act, observe, repeat). Feeding the failure report back so the model corrects itself is the idea behind Reflexion. The model never writes Blender code; it only chooses tool calls, which keeps it safe and checkable.

One-line answer: "An agent is an LLM that works in a loop: it calls tools to change the world, reads the results, and keeps going until the goal is met. Here the world is a Blender scene, the tools are 16 animation commands, and a checker tells it what is still wrong."
Big picture

Architecture

Arrows: the agent sends tool calls (JSON); each is validated, then run in Blender; the result comes back to the agent. When the agent is done, the checker reads the scene; a failing report goes back to the agent.

  • Validation (before): checks each tool call is well-formed (tool exists, arguments present, right types and values) before Blender sees it; a bad call changes nothing and returns an error the agent can fix.
  • Blender worker (the work): Blender running headless in the background, keeping one scene and carrying out each valid call: placing props, animating figures from the motion library, moving the camera, rendering.
  • Checker (after): reads the finished scene's real data (positions, joints, timeline, camera) and tests it against the request; a failing report goes back to the agent to fix, up to 3 times.
One line for the viva: "Validation catches badly written calls before they run, the worker carries out the good ones in Blender, and the checker proves from the scene data that the result matches the request."
Parts

Each component in a little detail

1. Task set

tasks.json

30 requests written before building, each with machine-checkable checks. Six categories following the animator's ladder: static layout, object motion, single figure action, sequences, figure + props, two figures + camera. Roles ("the table", "the walker") are matched to whatever names the agent chose.

2. The directors (agents)

agent/template.py, llm_agent.py, claude_agent.py

  • A0: keyword rules → fixed tool sequence (baseline, no AI)
  • A1/A2: qwen2.5 3b / 7b via Ollama, tool calling, temperature 0, seed 0, 8k context; ran on a Kaggle T4 GPU behind a Cloudflare tunnel
  • A3: Claude through claude -p, with only this project's MCP server as its tools

A1–A3 get the same system prompt: the tools, the 2D world, the actions, "make only what is asked".

3. Tools + validation

blender_worker/schema.py

16 tools: scene_reset, scene_state, add_primitive, add_asset, set_transform, set_material, add_light, set_camera, camera_move, keyframe, set_easing, set_frames, add_stick_figure, play_action, render_check, render_final.

Every call is checked against a JSON schema first; a bad call changes nothing and returns an error the model can act on. Helpers avoid arithmetic: {"on_top_of": "table"}, play_action(to="table"). A repeat guard answers a third identical call with "already done, do the next step".

4. Blender worker

blender_worker/worker.py, tools.py, client.py

Blender 4.5 LTS runs headless as one long-running process; Python sends it JSON commands over a local socket. It keeps one scene. Look: a flat 2D world: orthographic side camera, white background, ground line, Workbench renderer. Positions are [x, z]; depth is only a layer (back / middle / front). Output: MP4 at 24 fps plus an editable .blend.

5. Stick figures + motion library

blender_worker/motion.py

A figure is one curve object whose 18 joints are keyframed every frame. 17 actions:

  • Captured: walks (normal, happy, sad, worried) from Project 3's joint tracks; the wave from my own video
  • Keyed / computed: idle, look, look down, react, sigh, run, handshake, pick up / put down, sit / stand up, turn
  • Joining: eased blends, foot locked to the ground, settle step after walks, turn before acting, keep the last facing

6. Checker

checks/checker.py, figure_checks.py

sample_scene exports positions, joint tracks, the action timeline and the camera every frame (visibility and collisions every 6th frame). Plain Python then checks: 9 defaults for every task (in view, not hidden, on a surface, no hovering, no collisions, grounded ±1.5 cm, no foot slide ≤ 0.5 cm/frame, no pops, clip 2–20 s) plus the task's own checks (bounces, actions in order, reaches, camera move…). The report lists failures first, written for the agent.

7. MCP server (for Claude)

blender_worker/mcp_server.py

Model Context Protocol: an open way to offer tools to a model. Hand-written (JSON-RPC over stdio, no SDK). It offers the same validated tools plus check_scene, and attaches to the same Blender worker the evaluation uses, so the checker sees exactly Claude's scene.

8. Story mode

story.py

A story is split into shots, like a storyboard. Each shot is a short request continuing the same scene; the agent is told what exists and where the timeline ends. New characters appear when their shot starts; the camera is directed once at the end.

9. Demo + deployment

demo_app.py, space/build_static.py

Local Gradio app: Direct, Story, Task + checks, Results. Deployed as a free static Hugging Face Space (every final run, its calls, checks and clip). Live use: run_demo.bat gives a public link to the laptop.

Walkthrough

One request, step by step (real run)

Request p01: "a stick man walks to the table and waves", directed by Claude. Its actual tool calls:

add_asset        {"asset": "table", "name": "table", "location": [2, 0]}
add_stick_figure {"name": "man", "location": [-2.5, 0], "facing": "right"}
play_action      {"name": "man", "action": "walk", "to": "table", "start_frame": 1}
play_action      {"name": "man", "action": "wave"}
set_camera       {"look_at": [0, 1.6], "width": 8}
set_frames       {"start": 1, "end": 259}
check_scene  →  "All 11 checks pass."
  1. Request goes to the agent with the system prompt and the tool list.
  2. Agent decides the calls above. It never computes the walk distance: to="table" does that.
  3. Validation checks each call's names and types before Blender sees it.
  4. Blender worker builds the scene; play_action asks the motion library for the walk (foot locked, settle step), blends into the wave, and keys every joint every frame.
  5. Checker runs 11 checks: actions in order (walk then wave), reaches the table, in view, not hidden, on surface, grounded, no foot slide, no pops, no collision, no hover, clip length. All pass.
  6. Render: MP4 + .blend.

A fix from the report (m01: "a red ball bounces three times on the floor")

Claude keyframed the ball, then called check_scene: "bounces: ball bounces 2 time(s), expected 3" (its last bounce was too low to count). It raised the last bounce's keyframes, checked again: all 10 checks pass. That is the self-check loop working.

Where it started

Project 3 in one minute

  • Aim: animate a drawn 2D character from a character sheet (~10 views), drift-free (no video-generation model).
  • How: onboarding cut the drawing into body parts; a rig moved them with a motion library of 2D joint tracks; rendered on CPU.
  • What worked: the motion transferred to a second character with zero new animation work.
  • What broke: appearance. Flat drawings hide areas behind other parts; those had to be guessed, and the guesses showed as seams (e.g. a sleeve seam on a dark t-shirt). Every new character needed tuning.
  • Carried into Project 5: the walk tracks, the 18-joint skeleton, and the lesson that motion and appearance are separate.

Strengths

What went well

  • Checkable results: because the world is 2D and built by tools, every claim ("feet planted", "walks then waves") is verified from data, not by eye.
  • Tool design: placement helpers and targets turned hard geometry into simple choices; Claude needs ~6 calls per task.
  • Self-correction: Claude turned every one-line failure report into the right fix.
  • Stories: shot-by-shot directing scaled to 40–55 s animations with no errors.
  • Motion quality: animator rules (easing, foot lock, settle steps, facing) came from reviewing clips; each fix became a rule.
  • Reproducibility: all 120 runs replay to the same verdict; tests build broken scenes that must fail.
  • Cost: about a cent per second of finished animation.
Be honest

Limitations

  • A0's rules were written while looking at the 30 tasks, so 30/30 is a ceiling, not a fair score.
  • Study 2 and reworded held-out requests were planned but not run.
  • Checks confirm what was asked but don't forbid extras (qwen 3b's one fix also sat down).
  • One run per agent per task; Claude isn't deterministic (its earlier full run also gave 30/30, 27 first try).
  • Human rating was informal (my own review), not scored by independent viewers.
  • 2D only, side and front views; no physics, no faces on plain stick figures; a small prop library (the "lamp" is a table lamp).
  • Two changes after the feature freeze (rules learned new actions; a follow-camera bug fix), both re-checked against the eval.
  • Deployment is static; live directing needs my laptop (share link).
Takeaways

Learnings

  • An animation agent needs animation knowledge built into its tools. The quality came from animator rules, and most problems were spotted by watching clips.
  • Feedback only helps a model that can use it. The same report fixed all of Claude's failures and almost none of qwen's.
  • Good tools beat clever prompts for small models: every helper that removed arithmetic reduced errors.
  • Good characters need art made for rigging. I tried a dressed stick figure and a Gemini-generated cut-out puppet: cutting, hidden-joint filling and joint chains worked, but generated art was inconsistent (a head 15% too big, nothing drawn under overlaps). Project 3's lesson, confirmed from the other side.
  • Directing beats generating on control, editability and cost.
Next time

What could be improved or done better

  • Run Study 2 and held-out reworded requests; several runs per agent for variance.
  • A planner step for small models: list the story beats first, then make tool calls.
  • Checks that also forbid unrequested actions.
  • A scored human rating with several viewers.
  • More actions (jump, kick, push) and props (street lamp, house), each with its own check.
  • Drawn characters done properly: parts drawn whole on layers, matching side/front views, round overlapping joints.
  • A paid live server (Docker setup already built and tested) so live directing doesn't need my laptop.

Practice

Likely viva questions

What is your project, in one sentence?

An AI agent that turns a plain-language request into a short stick-figure animation in Blender, through 16 checked tools, checks its own result from the scene data and fixes what fails; I compare four directors on 30 tasks.

Why did you do this after Project 3?

Project 3 showed that motion transferred between characters but appearance broke. So I separated them: real software (Blender) does the rendering, stick figures keep appearance trivial, and the agent focuses on motion, timing and staging.

What is an agent? Is this really agentic?

An LLM in a loop that acts through tools, observes results and continues until the goal is met. Yes: it chooses tool calls, reads results and errors, and after the checker's report it fixes the scene itself. The rules baseline (A0) is not agentic; it's a fixed pipeline.

Why not use a video-generation model?

No control, no editable file, drift between frames, and 6–45× the cost per second before retakes. Here every result is an editable .blend and is checked.

Why not let the LLM write Blender Python directly?

Safety and checkability: arbitrary code can do anything and fail in unpredictable ways. Fixed tools are validated, give clear errors, hide hard math (walk to a target), and make results comparable across models.

How does the checker work? How do you know it's correct?

The worker exports positions, joint tracks, the action timeline and camera per frame; Python checks them (grounded within 1.5 cm, foot slide ≤ 0.5 cm/frame, actions in order, in view…). Test scenes that are deliberately broken (moonwalk, floating figure, ball through a table) must each fail exactly the expected check, and all 120 replays give the same verdicts.

Why do the qwen models fail?

Mostly bookkeeping: referring to objects before making them, missing arguments, repeating calls (347 times for 3b), raw coordinates that leave props floating, their own overlapping start frames, even resetting their scene. They also can't turn a failure report into the right fix.

Isn't the rules baseline's 30/30 unfair?

Yes, and the report says so: the rules were written looking at these 30 tasks, so it's a ceiling. In the live demo it silently dropped words it had no rule for ("sits down") until I added them. Rules only work as far as someone wrote them.

What is MCP and how does Claude talk to Blender?

Model Context Protocol, an open standard for offering tools to a model. I wrote a small MCP server (JSON-RPC over stdio) exposing the same validated tools plus check_scene; it attaches to the evaluation's Blender worker. claude -p runs with only these tools enabled.

How did you run qwen?

Ollama with qwen2.5 3b and 7b, temperature 0, seed 0. On the laptop CPU a task took 3.5–9.5 minutes, so the final runs used a Kaggle T4 GPU through a Cloudflare tunnel; Blender and the checker stayed on the laptop.

How is "first try vs after fixes" measured without a second run?

qwen runs at temperature 0, so its first round is exactly what it would do without the loop. Claude's first check_scene result is its first-try verdict. Both are recorded in the same run.

Where does the motion come from?

Walks from Project 3's 2D joint tracks; the wave from my own video; other actions keyed or computed from the scene (reach the ball, bend to the seat height). Joining uses eased blends, a locked planted foot and a settle step.

Why split stories into shots?

A long story in one request makes the agent plan everything at once and an early mistake breaks later beats. Shots keep each request small, like a storyboard; the camera is directed at the end over the whole timeline.

What would you do with more time?

Held-out requests and Study 2, a planner step for small models, stricter checks, more actions and props, and properly drawn characters (parts drawn whole, matching views).

How did you use Claude Code / AI in building this?

As a pair programmer for most of the code. I made the design decisions (2D world, tool scope, story mode, the feature freeze, stopping the puppet work), directed the experiments, and reviewed every clip; that review caught real bugs (unnecessary turning, handshake hands passing through each other, the camera trailing behind).

What was the hardest part?

Making motion look right between actions (blends, turns, foot locking), and the drawn-character attempt, where generated art lacked the hidden parts and consistency a rig needs.

What did you learn?

An animation agent needs animation knowledge built into its tools; feedback only helps a capable model; and good characters need art made for rigging.
