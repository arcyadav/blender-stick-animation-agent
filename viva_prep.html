Say this first

My 2-minute story

In Project 3 I tried to animate a drawn character from a character sheet. I cut the drawing into body parts and moved them with a library of motions. The motion part worked: the same motions worked on a second character with no extra animation work. But the look broke. When you cut a flat drawing into parts, some areas are hidden behind other parts and were never drawn, so I had to guess them, and the guesses showed up as seams.

So my lesson was: motion and appearance are two different problems.

In Project 5 I separated them. An AI agent directs animation inside Blender, a real animation program, using a small set of checked commands. The characters are stick figures, so only the motion matters. After each animation, a checker looks at Blender's own data: are the feet on the ground, did the actions happen in the right order, is everything in view? If something's wrong, the agent gets told and fixes it.

I compared four "directors" on the same 30 tasks. Claude got all 30 right, and fixed its own three mistakes after the checker told it what was wrong. The smaller open models got 8 and 3. Claude can also direct whole short stories, like a 54-second, 7-shot one with no errors, for about a cent per second of animation.

Concept

What's an agent?

A language model on its own just writes text. An agent is a language model that can do things: it has some tools (commands it can use), it uses one, looks at what happened, and decides what to do next, again and again, until the job is done.

Think of a film director who can't hold a camera. They give instructions ("put a table here, walk him to it"), the crew does it, they look at the result, and they give the next instruction.

Agent ideaIn my project
The goalThe request, e.g. "a stick man walks to the table and waves"
The brainThe language model (qwen or Claude) deciding what to do
The tools16 commands like "add a table", "add a stick figure", "make him walk", "set the camera"
The worldA Blender scene
What it sees backThe result of each command, or an error message
FeedbackThe checker's report: what's still wrong

The model never writes Blender code itself; it only picks commands from my list. That keeps it safe, and it means every result can be checked.

Say it like this"An agent is a language model that works in a loop: it uses tools to change something, looks at what happened, and keeps going until the goal is met. Here the tools are animation commands for Blender, and a checker tells it what's still wrong."
Big picture

How the pieces fit

  • Validation checks each command is written correctly before Blender sees it, like a receptionist checking your form is filled in.
  • The Blender worker carries out the good commands, like a film crew building the set and moving the actors.
  • The checker looks at the finished scene and tests it against the request, like a quality inspector measuring the product against the order.
Say it like this"Validation catches badly written commands before they run, Blender carries out the good ones, and the checker proves from the scene data that the result matches the request."
Parts

The parts, simply

The 30 tasks

30 requests I wrote before building anything, from easy to hard, in the order animators learn: place objects → bounce a ball → one action → a sequence of actions → acting with props → two characters with a camera move. Each task says what the checker must see.

In the code: tasks.json

The four directors

  • Rules: hand-written "if the request says X, do Y". No AI; it's the baseline.
  • qwen 3b and qwen 7b: small free open models. They ran on a free Kaggle GPU.
  • Claude: the big model, through Claude Code on my subscription.

All three AI directors get the same instructions and the same commands.

In the code: agent/

The commands (tools)

16 commands such as "add a table", "add a stick figure", "make him walk to the table", "move the camera", "render". I made them easy to use correctly: you can say "walk to the table" instead of working out distances, or "put the ball on the table" instead of giving coordinates.

In the code: blender_worker/schema.py, tools.py

Blender (the worker)

Blender, the real animation program, running in the background with no window. It keeps one scene open and does whatever command it receives. The look is a flat 2D world: side view, white background, a ground line. It saves an MP4 video and an editable Blender file.

In the code: blender_worker/worker.py

The stick figures and their moves

17 actions: walk (normal, happy, sad, worried), run, wave, idle, look, look down, a fright, sigh, handshake, pick up, put down, sit, stand up, turn. The walks come from Project 3's recorded motions, and the wave from a video of me. I added animator tricks so the moves join smoothly and the feet never slide.

In the code: blender_worker/motion.py

The checker

After the agent finishes, it reads Blender's data for every frame and tests it: feet on the ground, no sliding, nothing floating or passing through things, everything in view, actions in the right order. It writes a short report the agent can act on, like "the ball bounces 2 times, expected 3".

In the code: checks/

The MCP connection (for Claude)

MCP is a standard way to give a model a set of tools. I wrote a small MCP server so Claude can use my 16 commands, plus "check my scene". It talks to the same Blender the checker reads.

In the code: blender_worker/mcp_server.py

Story mode

For longer stories, the story is split into shots, like a storyboard. The agent directs one shot at a time, continuing the same scene, and the camera is planned at the end.

Who splits it? A person. The story is an input already written as shots: a JSON file in stories/, or the "Shots" box on the demo page. For each shot, the program tells the agent what already happened and what's in the scene now, and asks it to do only that shot. Splitting it automatically isn't built yet (see next steps).

In the code: story.py

Under the hood

From words to a tool call to Blender

1. How a sentence becomes a command

With every request, the model also gets a list of my commands: their names, what they do, and what information each one needs. Models like Claude and qwen are trained so that, when a command would help, they write a small structured block instead of a normal sentence:

{"tool": "play_action", "arguments": {"name": "man", "action": "walk", "to": "table"}}

It's still just text the model wrote, but in a format my code can read like a function call. My code runs it and sends the result back as text (e.g. "he walked from x = −2.5 to 1.3 in frames 1–120"). The model reads that and decides the next command.

2. How the command happens in Blender

By hand, you'd add a cube, move it, press I to set a keyframe at frame 1, go to frame 24, move it, and press I again. In Blender, every button is also a Python command, so code can do the same:

ball.location = (-2.0, 0.0, 1.5)
ball.keyframe_insert("location", frame=1)     # the same as pressing I at frame 1
ball.location = (0.0, 0.0, 0.0)
ball.keyframe_insert("location", frame=24)    # Blender fills in the frames between

"Walk him to the table" does what an animator would: finds the table, works out a walk that ends there, and sets a keyframe for every joint on every frame (thousands of key presses, automatically).

3. What "headless" means

Headless means running a program without its window. Started with blender -b, Blender opens no screen at all; it just runs my script and waits for commands. Like a kitchen with no dining room: orders go in, food comes out. It's faster, needs nobody to click, and can run on a server.

4. What a socket is

A socket is a connection between two programs so they can send each other messages, like a phone line. Blender runs as its own program and listens on a "port" (a room number on my laptop); my Python code connects to it and sends one command per line, and Blender answers with one result per line. That keeps one Blender and one scene open the whole time, and lets the agent's tools and the checker talk to the same scene.

Say it like this"The model gets descriptions of my commands and answers with structured commands instead of sentences. My code checks each one and sends it over a socket to Blender running in the background, where each command does in code what an animator would do by hand."
Under the hood

How a request travels through the system

  1. Browser → my app. The request is typed on the demo page. It goes to the app running on my laptop (through the public link if it's used remotely).
  2. App → Blender. The app starts Blender in the background and connects to it over a socket.
  3. App → the chosen director. Claude runs on Anthropic's servers and uses my MCP server to reach the commands; qwen runs on Ollama (on a Kaggle GPU) and gets the command list over the internet; the rules are plain Python.
  4. Each command → validation → Blender. Checked, then sent to Blender, which changes the scene and answers. The answer goes back to the model, which picks the next command.
  5. When it's done → checker. The checker reads the same Blender scene. If something's wrong, the report goes back to the model to fix (up to 3 times).
  6. Render → back to the browser. Blender makes the video, and the app shows it on the page.
Say it like this"The browser talks to my app, the app sends the request to the chosen model, every command the model makes is checked and passed to Blender running in the background, and at the end the checker reads that same scene before the video comes back."

The checker, in detail

Two different checks, at two different times

Validation also quietly cleans small slips, like "1" → 1 or {x, z} → [x, z]. The checker can't run after every command, because halfway through, the scene isn't finished: the ball exists but hasn't been made to bounce yet, so "bounces 3 times" would fail even though nothing is wrong.

For the small models, my code calls the checker when the model stops making commands. For Claude, the checker is a tool called check_scene, and Claude decides when to call it ("call it when you think you are done"). Either way, after the agent finishes, the evaluation runs the checker one final time, and that run decides pass or fail.

Step 1: Blender writes down the whole scene, frame by frame

A tool called sample_scene steps Blender's timeline through every frame of the clip (a 5-second clip at 24 fps is 120 frames) and writes down, for each frame:

  • every object's position, rotation, colour and box (its lowest and highest points)
  • where each object sits on the screen, as the camera sees it (0 to 1 across)
  • each stick figure's 18 joints, and what it's sitting on or holding
  • the camera's position and how wide it is

It checks every frame's data, not every frame's picture: nothing is rendered for the checker. Blender just moves to each frame and reads the numbers, which takes a second or two. One thing is only done on every 6th frame (and the last one): "is it hidden behind something?", because that means tracing lines from the camera to the object, which is slower. The few preview images (render_check) are for humans only; the checker never looks at them.

All of that goes out as one big block of data, and from here on the checker is plain Python, not Blender.

Step 2: Match the request's things to the scene's objects

Each task in tasks.json says what should exist and what must be true:

m01  "a red ball bounces three times on the floor"
roles:  ball = a sphere that is red
checks: bounces → ball, 3 times, on the ground

The agent might have called the ball ball, red_ball or sphere1. The checker ignores names: it finds whatever is a sphere and red, and treats that as "the ball". If several objects could fit, it tries every way of matching them up and keeps the one where the most checks pass. That's called binding.

Step 3: Each check is a small maths test on those numbers

Every check returns pass or fail and one plain sentence. The bounce check, for example:

  1. Take the ball's height above the ground on every frame.
  2. An arrival is a frame where it goes from in the air to touching (within 2 cm).
  3. It's a bounce only if the ball then rises clearly again (at least 5 cm), so a tiny wobble doesn't count.
  4. Count the bounces and compare with 3: "ball bounces 2 time(s) (frames [12, 30]), expected 3".

Other checks work the same way: row (are the cubes lined up?), middle of row (is the blue one in the middle?), spins (add up the rotation, ÷ 360 = turns), sits on (is the figure attached to the bench, hips at seat height?), action order (did he walk, then sit, then look up?).

Plus 9 checks on every task

These catch things that look wrong even when the request is met:

What comes out

2 of 12 checks fail:
- bounces: ball bounces 2 time(s) (frames [12, 30]), expected 3
- in_view: ball is outside the camera on 40% of frames

The sentences are written for the agent, so this report goes straight back to the model as its fix message.

Who wrote it, and why it isn't an AI

The checker is ordinary hand-coded Python with fixed rules and fixed tolerances (2 cm for "touching", 5 cm for a real bounce, 0.5 cm a frame for sliding). There's no model inside it, so the same scene always gets the same verdict. That's on purpose: if an AI judged whether another AI did the job, I couldn't fully trust the score. I built it with Claude Code as my coding assistant: I decided what to check and how strict to be, tested it on real runs and on deliberately broken scenes, and tuned the tolerances.

Say it like this"Blender writes down where everything is on every frame. The checker matches the request's things to the scene by kind and colour, not by name, and each check is a small test on those numbers, like counting how often the ball's height reaches zero and rises again. Failures come back as plain sentences the agent can fix."

I made these; they're not built into Blender

Blender has no "tools" for an AI. What it has is a Python interface called bpy: thousands of small functions like "create a mesh", "set location", "insert a keyframe". Each of my commands is a function in blender_worker/tools.py that wraps many of those into one simple, safe action:

My commandWhat it does with Blender's bpy
keyframeSets the value, then calls Blender's own keyframe_insert(). The closest to built-in.
set_easingChanges the interpolation on Blender's animation curves; "gravity" is my own
add_primitiveBlender's add-mesh, then moves it so its bottom sits at the height given, and gives it a flat colour
add_assetMine: a bench or tree is built from several shapes. Blender has no "bench"
add_stick_figureMine: builds the head, body and limbs and registers the figure
play_actionMine: asks the motion library for the poses, then keys them on every frame
camera_moveMine: works out the camera path, then keys Blender's camera
render_finalSets Blender's render settings (Workbench, flat 2D look) and calls Blender's render

Why wrap them instead of letting the model write bpy code? Simpler ("add a bench" is one call, not 30 lines, so even small models can use it), safer (every call is validated and no random code runs), 2D rules built in (things snap to the ground, fixed layers, the camera stays flat), and checkable (each command records what it did).

How many characters can be in a clip?

The code has no limit: add_stick_figure only needs each one to have a different name. I only tested up to two (handshake, waving together, one walking over to the other, walking side by side). With more, give each a different colour so the checker can tell them apart, make the camera wide enough, and remember there are only three depth layers and that handshakes are between two people. Crowds are future work.

Say it like this"Blender gives a raw Python interface. I designed 16 higher-level commands on top of it, so the agent works at the level of 'add a bench, make him sit', not meshes and keyframes."
Under the hood

The motion library

The model never moves joints. It picks an action by name, and blender_worker/motion.py (about 1,200 lines of plain Python, no Blender, so it can be tested on its own) makes it move properly. The model decides what happens; the library decides how it moves.

What "a motion" actually is

The stick figure has 18 joints: pelvis, chest, neck, top of the head, and left/right hip, knee, ankle, toe, shoulder, elbow and wrist. A pose is where each joint is in 2D: (forward, up). A motion is a list of poses, one per frame. Distances are in leg lengths (hip to ankle = 1), so the same motion fits a figure of any height.

The 17 actions and where each comes from

ActionsSourceStored as
walk, walk_happy, walk_sad, walk_worriedProject 3's recorded walk tracksJSON files
waveProject 3, taken from a video of me wavingJSON file
run, idle, look, look_down, react (fright), sigh, turnKey poses I wrote in code, exaggerated for a stick figureCode

1. Recorded: JSON files in motions/

Five folders (walk, walk_happy, walk_sad, walk_worried, wave), each with motion.json (the data) and meta.json (where it came from).

The walk is 36 frames at 24 fps: one 1.5-second step cycle that loops.

"joints": {
  "pelvis": [[0.0, 1.1536], [0.0333, 1.1598], [0.0667, 1.1613], ...],   36 (forward, up) pairs
  "chest":  [...],  "l_knee": [...],  "r_ankle": [...],  ...            18 joints
}
"stats": { "stride_per_cycle": 1.2, "bounce": 0.046, ... }

The wave is 154 frames at about 30 fps from my phone video. It stores angles instead of positions: how far the upper arm and forearm rotate on each frame (the forearm swings from about −5° to 138°). Its meta.json notes it came from my own video, with 154 of 189 frames used and an average tracking score of 0.77.

2. Keyed: a few poses in code, smoothed

Like an animator setting keyframes, these are a handful of key poses with times. The sigh, roughly:

0 s stand  →  0.8 s chest up, breathe in  →  1.6 s slump, head down  →  2.6 s back to standing

A function draws a smooth curve through the keys (a spline, the same idea as Blender's animation curves) to get every frame in between, and it never overshoots a key.

3. Computed: IK

Inverse kinematics: you say where the hand (or hip) should end up, and the code works out the shoulder and elbow (or knee) angles to get it there. "The ball is here" gives the pick-up; "the seat is this high" gives the sit; for a handshake, both hands meet in the middle.

Clean-up tricks

  • Toe lock: a planted foot stays exactly still, so walks don't slide
  • Braking: a walk slows over its last step instead of stopping dead
  • Blending: each action starts from where the last one ended, so there's no jump
  • Tempo: Project 3's walk was a slow stroll, so it plays 1.3× faster; the arms swing a bit more for the stick style

From the library to Blender

  1. The agent calls play_action("walk", figure, to="table").
  2. motion.py returns a pose for every frame (the walk cycle repeated until he gets there, feet locked).
  3. tools.py scales the poses to the figure's size, places them at its position and facing, and writes them as Blender keyframes on every frame, one for each point of the stick drawing.
  4. Blender just plays the keyframes back, and the renderer draws them.
Say it like this"A motion is 18 joints times N frames of (forward, up) positions, in leg lengths. The walks and the wave come from Project 3 and my own video, stored as JSON; the rest are key poses in code, smoothed with a spline, or worked out with IK. play_action turns them into Blender keyframes on every frame."
Where it started

Project 3 in one minute

  • What I tried: animating a drawn 2D character from a character sheet (about 10 views), without using any video-generation AI.
  • How: cut the drawing into body parts and moved them with recorded motions.
  • What worked: the motion. It worked on a second character with no new animation work.
  • What broke: the look. Parts hidden behind other parts had to be guessed, and those guesses showed as seams. Every new character needed fixing by hand.
  • What I kept for Project 5: the walk motions, the skeleton, and the lesson that motion and look are separate.
Method

What I tested

  • Which director is best? All four on the same 30 tasks, same commands, same checks.
  • Does the "fix it" step help? Compare how many tasks passed on the first try vs after fixing.
  • Why do the small models fail? Count which checks failed and what mistakes they made in their commands.
  • Can it do whole stories? Claude directed two main stories and three extra test stories, shot by shot.
  • Are the results repeatable? I rebuilt all 120 runs from their saved commands; every one gave the same pass or fail.

What goes in: the request text. What comes out: a pass/fail for every check, every command the director used, the time it took, and a video.

Planned but not done: removing the "look at the scene" command to see how much it helps, and testing the rules on reworded requests.

Strengths

What went well

  • Every result is checked from data, not judged by eye.
  • Easy-to-use commands meant Claude needed only about 6 commands per task.
  • Claude fixed its own mistakes from a one-line report.
  • Splitting stories into shots made long animations work.
  • The motion looks right because I added animator rules after watching every clip.
  • It's cheap: about a cent per second of animation.
Be honest

What's not perfect

  • The rules scored 30/30 only because I wrote them while looking at these tasks; it's a best case, not a fair score.
  • Two planned tests weren't run (see "What I tested").
  • The checker confirms what was asked but doesn't stop extra actions.
  • Each director ran each task once.
  • The motion was rated by me, not by a group of viewers.
  • Only 2D, with a small set of props (the "lamp" is a table lamp).
  • The live demo needs my laptop running.
Takeaways

What I learned

  • An animation agent needs animation knowledge built into its tools. The good motion came from animator rules, and I found most problems by watching the clips.
  • Feedback only helps a model that can use it. The same report fixed Claude's mistakes but not qwen's.
  • Good characters need art made for animation. I tried dressed stick figures and a drawn puppet from AI-generated parts. The method worked, but the generated art didn't match itself and had nothing drawn under the overlaps, the same problem as Project 3.
  • Directing beats generating for control, editing and cost.
Next time

What I'd do next

  • Run the two missing tests, and run each task several times.
  • Help small models by having them plan the story steps first, then make commands.
  • Add more actions (jump, kick) and props (street lamp, house).
  • Proper drawn characters: parts drawn whole, with matching side and front views.
  • Let the model write the storyboard itself from a one-line idea (below).

Automatic storyboards

Today a person writes the shots. Next, the model could turn "two old friends meet in a park" into the shot list itself.

  • Claude can already do this with just a prompt: it knows how stories and storyboards work.
  • Small models: splitting is a plain text task, much easier than directing (the many exact commands, positions and frames is where qwen fails), so qwen 7b would likely write usable shots before it could act them out.
  • The real problem is shots the system can perform, not just nice ones. "He remembers his childhood and smiles" is a lovely beat, but there's no "remember" action and no face. So the prompt gives the vocabulary (the 17 actions, the props, the 3 layers: "use only these"), simple rules (one or two actions per shot, name characters by colour, leave the camera to the end), two or three example stories, and forces JSON output so it always parses.
  • Check the storyboard automatically, like the commands: does every shot use only known actions and props? If not, send it back ("there's no 'dance', use one of …"). The same validation idea, one level up.
  • Fine-tune only if prompting isn't enough: have Claude write a few hundred idea → storyboard pairs and train qwen on them (LoRA). A small model learning from a big one is called distillation.
  • How to measure "good shots": a storyboard is good if the director can perform it, meaning the checker passes on its shots. That gives a score to compare prompting against fine-tuning.

Order: prompt with the vocabulary and examples → automatic storyboard check → fine-tune only if needed.

Practice

Practice questions

What is your project, in one sentence?

An AI agent that turns a plain request into a short stick-figure animation in Blender, using a set of checked commands, and checks and fixes its own work.

Why did you build this after Project 3?

Project 3 showed that motion works across characters but the look breaks. So I split the two: Blender handles the drawing, stick figures keep the look simple, and the agent focuses on the motion.

How are requests routed?

The browser sends the request to my app; the app sends it to the chosen model; every command the model makes is checked and then passed to Blender, which runs in the background; when it's done, the checker reads the same scene, and the video goes back to the browser.

What's an agent, and is this really one?

A model that works in a loop: it uses tools, looks at the result, and decides the next step. Yes: it chooses commands, reads the results and errors, and fixes the scene after the checker's report. The rules director is not an agent; it just follows a fixed recipe.

Why not just use a video-generation model?

You can't control it precisely, you can't edit the result, characters change between clips, and it costs much more per second. Here every result is an editable Blender file and is checked.

Why not let the model write Blender code directly?

Code can do anything and fail in unpredictable ways. A fixed set of checked commands is safe, gives clear errors, hides the hard maths, and makes models comparable.

How do you know the checker is right?

I built test scenes that are deliberately broken (a figure sliding, floating, a ball through a table), and each one must fail exactly the right check. And all 120 runs give the same result when rebuilt.

Why do the small models fail?

Mostly bookkeeping: using things before creating them, leaving out information, repeating commands, guessing coordinates so props float. They also can't turn the checker's report into the right fix.

Isn't the rules director's 30/30 unfair?

Yes. I wrote the rules looking at these tasks, so it's a best case. In the live demo it ignored words it had no rule for, like "sits down", until I added them.

What happens when a command fails?

If it's badly written, validation stops it before Blender and tells the model what's wrong. If it fails in Blender (e.g. "no object called bench"), that error goes back to the model too, and it tries again.

Where does each part run?

Blender, the app and the checker on my laptop; qwen on a free Kaggle GPU; Claude on Anthropic's servers through my subscription.

What is MCP?

A standard way to give an AI model a set of tools. I wrote a small MCP server that gives Claude my animation commands and connects them to Blender.

Why split stories into shots?

One long request makes the model plan everything at once, and an early mistake ruins the rest. Shots keep each step small, like a storyboard.

How did you use AI to build this?

I used Claude Code as a pair programmer for most of the code. I made the design decisions (the 2D world, the commands, story mode, when to stop adding features), ran the experiments, and watched every clip; that's how I caught bugs like unnecessary turning and hands passing through each other in the handshake.

What was the hardest part?

Making motions join smoothly between actions, and the drawn-character attempt, where the AI-generated art wasn't made for animation.

What would you do next?

Proper drawn characters on the same skeleton, more actions and props, and the two tests I didn't get to run.

SocketA connection between two programs so they can send messages, like a phone line

Foot lockKeeping the foot on the ground fixed so it doesn't slide
